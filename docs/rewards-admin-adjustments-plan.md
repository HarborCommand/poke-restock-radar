# Admin Reward Adjustments Design

Status: design only. Do not implement production mutation behavior until the owner approves it and Phase 1 rewards ledger behavior is merged.

## Goals

Admins should eventually be able to correct rewards safely without editing balances directly.

Supported adjustment intents:

- Add points.
- Subtract points.
- Cancel a pending reward.
- Reverse an incorrect reward.
- Add an internal reason and note.
- Preserve an audit trail.

## Non-Goals

- No redemption support.
- No customer-facing adjustment notes.
- No destructive ledger deletion.
- No direct manual edits to `RewardBalance`.
- No public API surface.

## Admin Access

All routes/actions must require:

- Existing admin authentication.
- Existing admin authorization guard.
- Server-side validation of all customer and order ids.

Client-provided customer identity, balance, or point totals must never be trusted.

## Proposed UI Placement

Add a collapsed "Reward adjustments" section to the admin customer or order detail view after Phase 1 is stable.

Fields:

- Customer account selector or locked customer context.
- Adjustment type:
  - add points
  - subtract points
  - cancel pending reward
  - reverse incorrect reward
- Point amount, when applicable.
- Related order, optional but recommended.
- Related ledger entry, required for cancel/reverse flows.
- Reason code.
- Internal note.
- Idempotency key generated by the server or form session.

Required helper copy:

> Reward adjustments are internal and ledger-backed. Do not use this for checkout discounts or customer service promises outside the rewards policy.

## Route Design

Suggested route:

```txt
POST /api/radar/customers/[customerAccountId]/rewards/adjustments
```

The handler should:

- Require admin auth.
- Validate customer account exists.
- Validate point amount is a positive integer where required.
- Require a reason.
- Require or generate an idempotency key.
- Load any target order or ledger entry by trusted ids.
- Execute in a transaction.
- Create exactly one `RewardLedgerEntry`.
- Update or recalculate `RewardBalance` transactionally.
- Return a sanitized admin DTO.

## Ledger Rules

Every adjustment must create a ledger row.

Recommended ledger types:

- `adjustment_add`
- `adjustment_subtract`
- `adjustment_cancel_pending`
- `adjustment_reverse`

Recommended metadata:

- Admin user id.
- Reason code.
- Related order id, if any.
- Related ledger entry id, if any.
- Internal note summary or note id.
- Idempotency key.

Do not store customer-facing promises or private payment data in metadata.

## Balance Rules

Add points:

- Creates a positive available ledger entry.
- Increments `availablePoints`.
- Product decision needed before incrementing `lifetimeEarnedPoints`.

Subtract points:

- Creates a negative adjustment entry.
- Decrements available points only up to the current available balance unless owner approves negative balances.
- Does not change pending points.

Cancel pending reward:

- Requires a target pending earn entry.
- Changes that entry or creates a cancellation ledger entry according to the final Phase 1 ledger convention.
- Decrements `pendingPoints`.
- Does not decrement available points.

Reverse incorrect reward:

- Requires a target ledger entry.
- Creates a negative reverse ledger entry with `reversalOfEntryId`.
- Adjusts pending or available balance according to the target entry state.

## Idempotency

Each submitted adjustment must use an idempotency key that is unique to:

- Customer account.
- Adjustment type.
- Target order or ledger entry.
- Point amount.
- Admin form submission id.

Repeated submissions should return the original adjustment result without creating another ledger entry.

## Audit Trail

Admin views should show:

- Date and time.
- Adjustment type.
- Points.
- Status.
- Reason.
- Admin actor.
- Related order or ledger entry.
- Internal note presence.

Private notes must remain admin-only.

## Validation Tests

Add tests for:

- Unauthenticated users cannot access adjustment route.
- Non-admin users cannot access adjustment route.
- Reason is required.
- Idempotency prevents duplicate ledger entries.
- Add points creates a ledger entry and updates balance transactionally.
- Subtract points cannot create an unsupported negative balance.
- Cancel pending rewards handles only pending entries.
- Reverse incorrect reward requires a target ledger entry.
- Customer-facing reward pages do not expose admin notes.
- No route directly edits `RewardBalance` without a ledger entry.

## Risk Areas

- Balance drift if ledger and balance updates are not transactional.
- Customer support confusion if adjustment notes leak.
- Duplicate point changes from double submit.
- Negative balance business policy.
- Lifetime earned semantics for manual admin additions.
