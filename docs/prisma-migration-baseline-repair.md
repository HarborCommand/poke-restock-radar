# Prisma Postgres Migration Baseline Repair

## Status

This is a draft remediation plan and verification harness. It does not change the active `prisma/migrations` history, the Vercel build path, or any existing database.

## Problem

The repository does not have an initial migration that creates the original schema. The first tracked migration, `20260613110511_checkout_customer_records`, starts with `ALTER TABLE` statements against `StorefrontCustomer` and `StorefrontOrder`. A brand-new Postgres database therefore cannot run `prisma migrate deploy` from empty state.

The original Postgres cutover followed the documented `prisma db push` bootstrap path. Existing Production was later baselined by verifying the live schema and resolving tracked migrations as applied. That makes the current Production history usable for additive deploys, but it does not make the repository bootstrappable for a new environment.

## Reviewed Baseline Artifact

`prisma/baseline/20260711_initial_postgres.sql` is a frozen SQL snapshot generated by Prisma from the Postgres form of `prisma/schema.prisma` at merge commit `8834156cec16e1d2173441e74eb35f7ce3ce829b`.

The companion manifest:

- records the reviewed SQL checksum;
- lists the 25 historical migrations absorbed by the snapshot;
- lets CI distinguish historical migrations from future additive migrations.

The SQL file is not in `prisma/migrations`, so normal `prisma migrate deploy` cannot execute it. It must never be run against an existing database.

## Empty Database Verification

The `Prisma baseline bootstrap` workflow starts a disposable local Postgres 16 service and runs `npm run prisma:baseline:verify`. The verifier:

1. rejects Production, remote hosts, unexpected database names, and missing confirmation flags;
2. proves the target has no tables;
3. checks the reviewed SQL checksum;
4. executes the frozen baseline;
5. resolves only the manifest's historical migrations as applied;
6. runs `prisma migrate deploy` so future migrations are exercised normally;
7. requires `prisma migrate status` to be clean;
8. diffs the resulting database against the current Postgres Prisma schema.

This gives schema and migration changes an empty-database bootstrap gate without using Production credentials or a shared Preview database.

## Proposed Active-History Cutover

Moving the baseline into active migration history is a separate owner-approved operation:

1. Freeze schema changes and take a verified Production backup.
2. Confirm Production has no failed migration rows and matches the reviewed baseline plus all later migrations.
3. Move the 25 absorbed migration directories to a permanent archive outside `prisma/migrations`.
4. Add the reviewed SQL as the first active migration.
5. On every existing database, verify schema parity before recording the new baseline migration as applied. Do not execute its DDL.
6. On a brand-new database, allow `prisma migrate deploy` to execute the baseline and every later migration.
7. Run the empty-database workflow and a cloned-data staging migration before any Production rollout.
8. Deploy the migration-history change in a controlled window with rollback artifacts ready.

The baseline must not be marked applied merely because a database is non-empty. Schema parity, constraints, indexes, migration checksums, and failed-migration state must all be verified first.

## Production Boundaries

- No `prisma db push` against Production.
- No `prisma migrate reset` against any persistent environment.
- No migration row edits or manual SQL in Production from this draft PR.
- No replacement of the current Vercel migration command until the active-history cutover is reviewed and approved.
- New schema work continues to require additive, reviewed migrations.
